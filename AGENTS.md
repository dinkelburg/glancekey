# GlanceKey

Unlock Ruben's Mac and Linux (Omarchy) machine with Face ID on his iPhone, from anywhere. See README.md for setup and the security model.

## Layout

- `Core/`: Swift package shared by the iOS and Mac apps. `Protocol.swift` (wire format), `Authenticator.swift` (pairing, single-use nonces, signature checks), `RelayClient.swift` (phone side), `FreeTier.swift` (the free version's limits and daily count), `FakePhone/` (CLI stand-in for the iPhone).
- `Mac/`: menu bar app. `RelayConnection.swift` keeps the outgoing WebSocket; `ScreenController.swift` types the password into the lock screen; `PasswordStore.swift` keychain + OpenDirectory check; `ControlSocket.swift` the Unix socket the sudo checker talks to (approvals live in `AppModel.swift`); `PasswordDialog.swift` finds and fills system password dialogs (coreautha "… is trying to unlock", SecurityAgent admin dialogs) through Accessibility; `AppIcon.icon` the app icon in Icon Composer's format (JSON plus an SVG), because macOS 26 and later show icons in the older format inside a gray square; `MenuBarIcon.swift` the same keyhole as a one-color menu bar icon, dimmed while the Mac can't be unlocked. `Mac/PAM/`: `pam_module.c` (macOS has no pam_exec, so this runs the checker for sudo) and `pam_check.c` (tests PAM with it); built by `scripts/build-mac-helpers.sh` into the app's `Contents/Helpers` (a build phase in project.yml) and excluded from the app target. The menu's sudo **Turn on…** (`AppModel.setSudoApprovals`) runs them as root through macOS's admin prompt, after copying them to a root-owned folder and checking they're signed by the app's own team; `scripts/enable-mac-sudo.sh` does the same from the source.
- `iOS/`: iPhone app. `DeviceKey.swift` (Secure Enclave signing key and password key per pairing, Face ID only), `Biometry.swift` (says Touch ID on iPhones that have it), `PrivacyInfo.xcprivacy` (Apple's privacy manifest: no tracking or data collected, UserDefaults for the app's own settings; keep it true to the code), `PhoneModel.swift` (pair/unlock/lock, smart unlock for Siri and Shortcuts, approvals, unlock all, live refresh while open, notifications), `ContentView.swift` (a row per computer with one button, a page per computer, Settings behind the gear; opening the app no longer unlocks by itself, since the Lock Screen card covers that), `PhoneApp.swift` (`AppDelegate`: push token, notification taps), `Intents.swift` (Shortcuts/Action button). The subscription (README "Free version and subscription"): `Store.swift` (StoreKit, the free limits and today's count, all on the iPhone; limits only for the App Store/TestFlight app on our relay), `UnlimitedView.swift` (Apple's subscription screen, offered before Face ID when an unlock, approval or pairing goes over the free limits), `Unlimited.storekit` (the products for running from Xcode). The Lock Screen card (a Live Activity): `Shared/LiveCard.swift` (its content and its links; also compiled into the widget extension), `LiveCardController.swift` (starts it, updates it while the app is open, registers it on the relay). The card's buttons (Unlock, Lock, Approve) are links that open the app (`PhoneModel.open`), which runs Face ID. Deny isn't on the card, so the command gets the room; it's in the app, a tap on the request away. Tested on a real iPhone: a button running in the background can't use the Face ID key, neither by counting the Face ID that unlocked the iPhone nor by showing its own prompt (iOS only shows an app's Face ID while it's on screen). Don't reintroduce a second key that the passcode can unlock to get around that: Ruben rejected it.
- `iOSWidgets/`: the widget extension (target `PhoneWidgets`) that draws the card on the Lock Screen and in the Dynamic Island. iOS cuts a Live Activity off at 160 points, so it shows as many rows as fit.
- `linux/`: Go agent (`glancekey-agent`), static binary, systemd user service. Lock screen backends in `screen_linux.go`: Omarchy's Quickshell lock (types with `wtype`; no unlock IPC exists), hyprlock (`SIGUSR1`), logind (GNOME/KDE). Off Linux it uses a fake screen for testing. `seal.go`: the saved password is encrypted ("sealed") to each paired iPhone's password key and kept in `agent.json`; a plain copy stays in the GNOME keyring until every paired iPhone has opened its own sealed copy once, and each unlock seals it again under a fresh key (`set-password` and `forget-password` go through the running agent, or work on the state file when it isn't running). `card.go` sends the agent's part of the Lock Screen card when it changes. Approvals: `approvals.go` (agent side, notifications), `checker.go` (`glancekey-agent pam`, the root-owned checker PAM runs on Linux *and* on the Mac), `sudo_setup.go` (`enable-sudo`/`disable-sudo`), `procinfo_*.go`.
- `relay/`: Cloudflare Worker + Durable Object per machine at https://relay.glancekey.com (DinkelWorks account). The old https://glancekey.dinkelworks.nl stays on the same Worker for installs and pairings that still use it. Only routes; not trusted. It also sends the APNs notifications computers ask for over their WebSocket (`notify`), with the APNs key in the Worker secret `APNS_KEY` (README "Notifications"); a `Recipient` Durable Object per push token (by its SHA-256) caps what one iPhone gets from all computers together, since anyone can claim a new machine id. It keeps the iPhones' Lock Screen cards: one `Card` Durable Object per iPhone stores each computer's latest part (`card`), only from computers that iPhone registered, and pushes the card as a Live Activity (README "Lock Screen card"). One relay pushes the whole card, so the iPhone registers it on one relay (ours if any computer uses it) and gives the card id only to computers on that relay; the others notify as usual. For an iPhone with a card it also does the notifying: computers leave that iPhone out of `notify`, and the card alerts for a new request, or the `Card` sends the regular notification when there's no card. `GET /v1/limits` tells the iPhone app the free limits (`FREE_LIMITS` in wrangler.jsonc); the relay never sees use or purchases.
- `site/`: the landing page and privacy policy at https://www.glancekey.com (static files in `site/public`, served as a Cloudflare Worker with static assets, DinkelWorks account). Redirect Rules in the glancekey.com and dinkel.works zones (Cloudflare dashboard, not in this repo) send glancekey.com and the old glancekey.dinkel.works there, with proxied `AAAA 100::` records so those names reach Cloudflare. Pages: home, `docs.html`, `download.html`, `privacy.html`, and `install.sh` (the Linux one-line installer). `site/downloads` is another Worker serving https://download.glancekey.com from `build/downloads` (not in git); only `scripts/release.sh` deploys it. No JavaScript, cookies, third-party requests or request logs; the CSP in `public/_headers` enforces the first three. Its claims (open source, self-hostable, no data collected, the security model, what the relay sees and stores) must stay true to the code: update the page when those change.
- `project.yml`: source of truth for the Xcode project (`xcodegen generate`; the .xcodeproj and Info.plists are generated and not committed).

## Keep in sync

`Core/Sources/AppCore/Protocol.swift` and `linux/protocol.go` implement the same protocol (field names, signed message bytes incl. `ApprovalMessage`, pairing HMAC, error messages in `Authenticator.swift` ↔ `linux/auth.go`, and `RelayNotification` (incl. `expiresIn`) and `RelayCard`, which `relay/src/index.ts` reads). `PairedDevice.keyFingerprint` and `keyFingerprint` in `linux/auth.go` (the short key fingerprint the iPhone, the Mac menu and `enable-sudo` show) are pinned in both test suites, and `Approvers` devices carry an optional RFC 3339 `pairedAt` on both sides. The card's content (`LiveCardAttributes.ContentState` in `iOS/Shared/LiveCard.swift`, decoded by ActivityKit) is built as JSON by the relay's `Card` (`contentState`), and its `attributes-type` is that struct's name. `WaitMessage` and `waitMessage` (the signed approval wait) are pinned in both test suites too. `FreeLimits` (`Core/Sources/AppCore/FreeTier.swift`) is the JSON of the relay's `/v1/limits`, pinned in the Swift and relay tests. `Core/Sources/AppCore/PasswordSeal.swift` and `linux/seal.go` implement the sealed password (key derivation, AES-GCM layout, `SignedMessage` v2 and pairing proof v2, which cover the password key, the session key and the wrapped key). The cross-language test vectors and the pinned JSON in both test suites must keep passing. The control-socket messages (`approvers`, `approval`, checker lines) in `Mac/ControlSocket.swift` match `linux/control.go` and `linux/approvals.go`, because the same Go checker talks to the Mac app.

The app's name is defined only in `Core/Sources/AppCore/Brand.swift`, `linux/brand.go`, `project.yml` (`APP_NAME`/`APP_ID`; the scripts read them through `scripts/brand.sh`), `relay/src/index.ts` (`APP_NAME`), `relay/wrangler.jsonc` and `iOS/Unlimited.storekit`. Code uses those constants and never spells the name out; `scripts/check-brand.sh` (part of `scripts/test.sh`) fails otherwise. Docs (`*.md`) and the website (`site/`) spell it out, so update them by hand after a rename. Changing the display name is cheap. Changing the id changes bundle IDs, keychain items, the URL scheme, the subscription's product IDs and the paths on the computers, so everything has to be paired and set up again. The `faceunlock…/v1` prefixes in signed messages and the pairing proof are fixed protocol constants from the app's first name (FaceUnlock), not branding: leave them.

Approval trust model: for sudo/polkit the checker (root) creates the nonce and verifies the signature against root-owned `approvers.json`; the agent, Mac app and relay only carry messages. Keep it that way: nothing user-level may decide a sudo approval. The one thing the user level does decide is how long the checker waits (the approval wait, `ApprovalWait`/`wait.go`): the Mac app or agent keeps it, as the source of truth, and hands it to the checker with each request; the iPhone changes it with a signed `setWait` command. A longer wait can't approve anything. Mac password dialogs are the exception by design: the Mac app verifies those itself (same trust as unlock, since it holds the password anyway), types only into Apple-signed coreautha/SecurityAgent (code-signature check) and only via `postToPid`. The iPhone never approves without a tap on Approve.

On the Mac, the iPhones that may unlock, fill dialogs or become sudo approvers are the ones listed in the password's own keychain item (`PasswordStore`), not the UserDefaults list: any program running as Ruben can overwrite UserDefaults and keychain items (without reading them), but not with the right password, which OpenDirectory checks before the list counts. Change that list only through pairing, removing and saving the password. Saving keeps the old list only if the old password still checks out (or is the same); otherwise (Ruben changed his Mac password, or an old item without a list) the list starts empty and the menu asks to confirm each iPhone by its key fingerprint (`AppModel.trust`, kept only in memory). The checker only shows a sudo request whose arguments it read for certain and whose first argument is sudo; anything else gets the password prompt. The menu's **Turn on…** passes those iPhones to `enable-sudo --approvers` and names them in the admin prompt; from a terminal, `enable-sudo` lists them (marking new ones) and asks first.

## Commands

- All tests: `scripts/test.sh`
- Mac app: `scripts/build-mac.sh` (builds, installs to ~/Applications, restarts it)
- iPhone: `scripts/install-iphone.sh` (cable or paired device; Ruben's paid Developer Program team U78YQGE72M, so an install keeps opening for a year)
- TestFlight and App Store: `scripts/upload-testflight.sh` archives the iPhone app and uploads it to App Store Connect (app GlanceKey, Apple ID 6827081602). The build number is the date and time.
- Linux binaries: `scripts/build-linux.sh` → `build/linux/`
- Mac and Linux release: raise `MARKETING_VERSION` in project.yml (the iPhone app's version is `IPHONE_VERSION`), then `scripts/release.sh`: notarizes the Mac app (Developer ID), publishes it and the Linux program on download.glancekey.com and updates the public Homebrew tap github.com/dinkelburg/homebrew-glancekey. Downloads stay until the next release replaces them.
- Relay: `cd relay && npx wrangler deploy`. A deploy briefly drops every agent connection; they reconnect within seconds.
- Website: `cd site && npm install && npx wrangler dev` (http://localhost:8788) to preview, `npm run deploy` to publish.
- End to end without devices: run the Go agent on the Mac (fake screen) and pair `fake-phone` with it; see README "Development" (also covers approvals and the Mac PAM module via `pam-check --direct`, no root needed).
- sudo approvals: Linux `sudo glancekey-agent enable-sudo`; Mac the menu's **Turn on…** or `scripts/enable-mac-sudo.sh` (Ruben does it; it needs his password and edits `/etc/pam.d/sudo_local`).

## Gotchas

- Keychain access and the Accessibility grant are tied to the Mac app's signature. `scripts/build-mac.sh` signs with Apple Development, downloads with Developer ID: switching between the two, or ad-hoc signing, loses both once. The Mac app has the hardened runtime on (notarization needs it); Developer ID builds also drop the debugging entitlement.
- Simulator builds need signing for the keychain: `CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=YES`.
- In tests, never lock or unlock the real Mac screen unless Ruben asks; use the Go agent's fake screen. Don't change `/etc/pam.d` on the real Mac in tests; real Linux PAM can be tested in a Docker container.
- A harmless password dialog for testing: a tiny Swift tool calling `LAContext().evaluatePolicy(.deviceOwnerAuthentication, …)` (coreautha) or `osascript -e 'do shell script "true" with administrator privileges'` (SecurityAgent). The Mac app asks the real iPhone about it, so tell Ruben first. These SwiftUI dialogs expose button labels as AX descriptions and report the secure field's contents via AXValue (never log it).
- macOS has no `pam_exec`; a PAM module that fails to load breaks sudo entirely, which is why `enable-sudo` tests it through a temporary `/etc/pam.d/glancekey-check` first.
- The repo is public (AGPL-3.0, `LICENSE`). Never commit keys, tokens, passwords, App Store Connect details or personal data such as addresses and phone numbers; the APNs key lives only in the Worker secret and 1Password. Pull requests aren't taken (README "Contributing"), so don't merge outside code.
