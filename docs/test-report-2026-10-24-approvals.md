## Bugs and suggested fixes

1. **Polkit silently omitted on vendor-PAM layouts.** `linux/sudo_setup.go:27`, `linux/sudo_setup.go:143`–145. Minimal repro on either clean tested distro: install polkit, confirm `/usr/lib/pam.d/polkit-1` exists and `/etc/pam.d/polkit-1` does not, then run enable-sudo with a paired running agent. It reports success but never enables polkit. Suggested fix: when the /etc override is absent, discover the distro's vendor service file, copy its effective stack into an /etc override with the FaceUnlock line, and track that the override was newly created so disable removes it and restores vendor fallback. Do not modify package-owned /usr/lib files in place. Include this layout in setup tests. Current Arch vendor stack uses `auth/account/password/session include system-auth`; Debian uses `@include common-auth/common-account/common-password/common-session-noninteractive` plus pam_env session lines. Sudo originals were Debian's `@include common-auth` layout and Arch's `auth include system-auth` layout.

2. **Unreadable sudo environment silently disables SSH detection in default Docker.** `linux/procinfo_linux.go:18` and `linux/checker.go:70`–75. Minimal repro: ordinary Debian container without CAP_SYS_PTRACE, enable-sudo, then interactive `env SSH_CONNECTION=test sudo -k /usr/bin/id -u`. It waits the full approval timeout instead of skipping. Reading the *live checker's parent* environment as container root independently returned `Permission denied`; processInfo discards that error and returns an empty environment. Suggested fix: propagate environment-read failure and handle it explicitly (conservatively fall through to password if remote/local status cannot be established), or obtain the remote marker from a reliable PAM/caller channel. Add a capability-restricted integration test. This result **does not establish failure on a normal Linux host with full root capabilities**; the convenience behavior fails in the tested Docker configuration. No authentication bypass was demonstrated.

3. **Killing sudo leaves an orphan checker and a stale approval.** `linux/checker.go:108`–110; agent cancellation is at `linux/approvals.go:140`. Minimal repro: enable-sudo, start interactive sudo with a 30-second wait, confirm one hello approval, `pkill -KILL -x sudo`, and query hello after 0.5 s. It still lists one; the checker is reparented and retains its socket. Killing the checker removes the approval immediately. Suggested fix: tie the checker to the requesting process lifetime, for example Linux PR_SET_PDEATHSIG with the usual parent-race recheck, or a parent-liveness watcher that closes the socket/exits. Cover abrupt parent death separately from checker socket hang-up. Tested with SIGKILL; Ctrl-C/normal terminal cancellation was not certified.

4. **Rosetta argv breaks `sudo -S` detection and request titles (emulated Arch only).** `linux/procinfo_linux.go:16`, `linux/checker.go:254`, `linux/checker.go:301`. Minimal repro: run archlinux:latest amd64 on this ARM64 Docker Desktop, enable-sudo with updated checker, set timeout 5s, then feed the test password into `sudo -k -S /usr/bin/id -u`. It still waits **5.41 s**. Process inspection shows argv beginning `/run/rosetta/rosetta /usr/sbin/sudo sudo -k ...`; the parser sees the executable path as the command and stops before `-S`. Approval titles likewise become `sudo /usr/sbin/sudo sudo -k /usr/bin/id -u`. Suggested fix: normalize known emulator/interpreter prefixes before parsing sudo options and formatting the title, with an integration vector for this argv layout. **Do not infer this fails on native Omarchy/Arch**; native Debian's new stdin behavior passed.

No source patches were made for these findings.

### Round-2 bug disposition and harness notes

No new product bug or source fix proposed. The original fixes were exercised at `linux/sudo_setup.go:171` (vendor creation), `linux/sudo_setup.go:120` (override removal), `linux/checker.go:277` (SSH ancestry), `linux/checker.go:249` (parent lifetime), and `linux/checker.go:294` (emulator normalization). A bare synthetic SSH environment variable with unreadable sudo environment was deliberately not the SSH criterion; tested actual SSH.

Arch OpenSSH 10.6p1 failed before login with **`ssh_sandbox_child: prctl(PR_SET_SECCOMP): Invalid argument [preauth]`**. Installed gcc only in the disposable container, built `/tmp/sshd-rosetta.so`, and ran `LD_PRELOAD=/tmp/sshd-rosetta.so /usr/sbin/sshd -D -e`. The shim returns success only for `PR_SET_SECCOMP`, forwarding other prctl calls to the syscall. It was confined to sshd's container environment; setuid sudo discards LD_PRELOAD. The qualified PASS exercises real SSH with its unsupported sandbox disabled; it does not certify unmodified OpenSSH on Rosetta. Shim/compiler removed with container. Suggested harness improvement: use an init/subreaper from the start so zombies do not obscure checker-cleanup assertions.

An initial direct `docker exec ... pkexec` had a parent outside the PID namespace; Debian asserted a positive subject start time, exit **134**. Kept a shell parent alive inside the container (`pkexec ...; result=$?; exit $result`); reported polkit results use that corrected harness. This was not a FaceUnlock regression.
